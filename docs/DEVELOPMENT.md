# Development notes from the original project

For this project, I developed a warehouse inventory application whose basic purpose was fairly straightforward: allow a user to create an account, log in, and manage inventory through ordinary CRUD operations. The application allows inventory records to be created, viewed, updated, and deleted, while also tracking when an item reaches zero stock and supporting SMS alerts for that condition. The intended user was a warehouse employee who needs to make frequent, relatively simple changes without spending much time navigating the software itself. That pushed the application toward a direct interface where the relevant stock information remained visible and ordinary actions were easy to find.

The application therefore used a small number of screens and deliberately shallow navigation. The login screen handled account creation and authentication, while the inventory screen became the center of nearly everything else. A RecyclerView displayed inventory records, individual rows could be selected for editing, deletion was clearly separated as a more consequential action, and Add Item opened a small dialog rather than sending the user through another screen. Search and zero-stock filtering were also kept on the main inventory page. The general design principle was that a warehouse employee should be able to find the relevant item, make the necessary change, and return to the physical work with as little interference from the application as possible.

My development approach was to establish the broad architecture first and then build the application in working layers. Persistent account creation came before database-backed login, the SQLite inventory database came before replacing the original dummy RecyclerView data, and CRUD functionality was completed before adding search, filtering, and notification behavior. That made debugging considerably easier because each new piece had a smaller number of possible failure points. I also relied heavily on documentation, Android Studio, and AI assistance for unfamiliar Android APIs and boilerplate, while still needing to understand how the Activity, adapter, database helper, listener, and permission systems fit together well enough to recognize when a suggested implementation did not belong where it had been placed.

Testing was mostly iterative rather than something reserved for the end. After each major change, I ran the application in the Android Emulator and tested the relevant path, including account persistence, valid and invalid login attempts, adding and editing inventory, deleting records, search behavior, zero-stock filtering, and SMS-permission behavior. That process repeatedly exposed small edge cases that were not obvious while writing the code, which reinforced how easily a program can appear correct along its intended path while still behaving strangely as soon as the user does something slightly different.

The largest challenge was becoming comfortable with Android’s division of responsibilities. Android development relies heavily on framework objects, callbacks, lifecycle methods, adapters, permission systems, and operating-system services, and many of those abstractions were unfamiliar when I began the course. The challenge was therefore often less the underlying programming logic than learning which Android component owned a particular responsibility and how data was expected to move between them. Once that structure became clearer, the project became much easier to reason about.

The strongest part of the finished application is the inventory-management system itself. The RecyclerView, InventoryItem model, adapter, and SQLite database helper work together to provide persistent CRUD operations while keeping the database’s internal IDs hidden from the user. Search, zero-stock filtering, confirmation before deletion, and the notification trigger were then layered over that same structure rather than implemented as unrelated features. That portion of the project best demonstrates the software-engineering skills I developed during the course because it joins persistent data, UI behavior, user-centered design, and Android-specific architecture into one working system.
